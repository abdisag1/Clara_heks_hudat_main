# Review of the v2.2 firmware

This lists the defects found in the v2.2 sources (in [`legacy/v2.2`](../legacy/v2.2))
that motivated the rewrite. The timer findings were confirmed by running the exact v2.2
timer set-up on the simavr simulator with the stock Arduino AVR core (1.8.x).

> If your v2.2 units behave differently from what is described in 1.2 and 1.3 (for
> example, production starts by itself when the bottle is filled), the firmware on them
> is not built from these sources. Please check before relying on field data.

## 1. Timing

### 1.1 Timers configured before the Arduino core initialises them

`Wata::init()`, `Levelsensors::init()`, `Ecophi::init()` (main board) and
`Dosage::init()`, `I2c::init()` (dosing board) program Timer0/1/2. They are called from
the constructors of **global objects**, which run before `main()`. `main()` then calls
the Arduino core's `init()`, which reprograms the same timers for `millis()` and
`analogWrite()`. The resulting interrupt rates, measured in simulation over 2 s:

| Timer | Intended | Actual | Consequence |
|---|---|---|---|
| Timer0 COMPA (main) | 1 ms | 1.024 ms | production "second" = 1.024 s; "minute" = 59 × 1.024 s = 60.4 s; a 180 min batch lasts ~181.3 min |
| Timer1 COMPA (main) | 1 Hz | **never fires** | `Levelsensors::run()` never samples the sensors, so the level states are never updated |
| Timer2 COMPA (main) | 8 kHz | 244 Hz (4.1 ms) | Ecophi "minute" = 30.7 s; a frame every ~31 s instead of every minute |
| Timer1 COMPA (dosing) | 1 Hz | **never fires** | the 20 s dosing calculation in `Dosage::run()` never executes |
| Timer2 COMPA (dosing) | 8 kHz | 244 Hz | I2C data refreshed every 1 s instead of every 31 ms (harmless) |

Timer1 never fires because the core switches it to 8-bit PWM mode (TOP = 255), so the
compare value 15624 is never reached.

### 1.2 Timer bookkeeping

* The tick counters (`wa_timer`, `mytimer`, `eco_timer`, ...) are 16-bit `int`s, changed
  in interrupts without `volatile` and read without disabling interrupts (torn reads).
* `wa_timer` is only reset while a phase is active. In standby it overflows (undefined
  behaviour) after ~33 s.
* A production "minute" is counted at `wa_timer_s >= 59`, while settling and transfer
  use `>= 60`.
* The dosing board's flowmeter interrupt writes `TCNT1 = 0` on every pulse, which also
  disturbs Timer1.

### 1.3 Pump pulses in a busy loop

`Pump::run()` makes one step per `loop()` pass by busy-waiting `clara.period` µs
twice. Everything else in `loop()` (the flowmeter's `Serial.print` every second, I2C)
adds to the step period, so the delivered dose is always lower than calculated, and
worse at high flow. Because of 1.1, `clara.period` also never leaves its initial
1000 µs, and the ENABLE pin (active low) is only driven low by the code that never runs.

## 2. Dosing

* **Calibration never reaches the dosing board.** The main board sends 7 floats
  (28 bytes); the dosing board only accepts a frame of exactly 8 floats (32 bytes), and
  even then ignores the values. The dosing board therefore always used its hard-coded
  constants, whatever was set with `set 3..9` on the main board.
* The master requests 32 bytes and the slave answers 16; there is no checksum, so a
  disturbed transfer is displayed as valid data.
* `Flowmeter::read_flow()` divides by `pulse_count_flow` without checking for zero.
  With no flow, `average_pulse` is garbage.
* The flow coefficient `if/else` chain has a gap: exactly 160 L/min gives coefficient 1.0.
* The step count is truncated every interval (systematic under-dosing at low flow).
* The Kp/Ki parameters of the documented "PI controller" are not used anywhere.

## 3. Main board

* `Levelsensors`: `const bool numReadings = 10` evaluates to `true` (1), so the
  sample arrays have **one** element while the loops read indices up to 14 and 19
  (buffer over-read). Level 1 and levels 2/3 are also evaluated with different logic.
* The production time was never loaded from EEPROM (`clara.pr_time_min = ...` is
  commented out), so it was always 180 min. The progress saved every 30 min was written
  over parameter 0 and never used at start-up, so a power cut restarted the batch.
* `Clara::get_ph_value()` returns the active-chlorine value.
* `Display::run()` calls `delay(5000)` (blocks everything for 5 s) and `lcd.clear()`
  every 2 s (flicker). Each refresh builds a dozen `String` objects (heap
  fragmentation on the AVR). Target FRC is labelled g/L instead of mg/L.
* `Calibration`: `Serial.readBytesUntil()` blocks the loop for up to 1 s and does not
  NUL-terminate the buffer, so a short command keeps the tail of the previous, longer
  one. A missing argument passes `NULL` to `atoi`/`atof`, and `cal` and `get` are
  always followed by the error message "Invalid command".
* `Voltagesensor`, `Calibration`, `I2c` and `Ecophi` constructors contain no-op
  statements such as `this->pin;` (the pin is never stored).
* `Serial.begin(9600)` and `pinMode()` are called from constructors of global objects,
  before the core is initialised (six objects on the main board, four on the dosing board).

## 4. Structure

Global mutable state is spread across files (`int i`, `j`, `x`, `k`, `flag`, ... at
file scope). Every object depends on the `Clara` "god object". Nothing can be tested
without hardware. v3 addresses this with hardware-independent libraries, explicit
interfaces and host tests. See the [README](../README.md).
